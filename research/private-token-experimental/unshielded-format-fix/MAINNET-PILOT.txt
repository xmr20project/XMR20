3. CUSTODY DECISION
   The pilot uses the compiled xmr20_joint_escrow program in OPERATOR-VERIFIED mode (operator = policy owner = verifier; one
   signer), exactly what bridge/custody-rpc.mjs implements: deposits by holders into the pool vault, redemptions signed by the
   operator keypair, one receipt per nonce. The existing live bridge custody is NOT reused (different system; a new adapter and a
   separate review would be needed). Legacy backing for migrated holdings is deposited by the operator into the same vault
   (the operator journal accounts for it as unclaimed legacy rights). Mainnet deployment of the program (about 1.5 SOL rent)
   and the policy initialisation are OWNER actions with a mainnet keypair; nothing here does them.
   Rehearsal: rehearsal/custody-rehearsal.mjs runs the full adapter path (deploy, Token-2022 mint with a 1.5% transfer fee,
   policy, holder deposit, receipt, operator redemption, exactly-once, reserve) on a disposable LOCAL solana-test-validator
   started with mainnet's current SBPF deployment rule. Result: PASSED (attempt 7, 26 Oct 2026) — deposit receipt net 98,500,000 of 100,000,000; redemption 40,000,000; duplicate nonce
   refused; reserve 58,500,000 (RESULTS-FIX.txt section 6, runs/custody-rehearsal-local.json).
   Devnet: same script with --url https://api.devnet.solana.com --payer rehearsal/devnet/payer.json; the throwaway payer
   9vDssanKFdMsv5ccejppDBuKkMcPSGEFnXbpAjxbwb23 has no SOL (airdrop rate-limited twice on 26 Oct); send devnet SOL to it from
   faucet.solana.com to run it.
   Program artefact: SBPF v0. SIMD-0500 (disable deployment of SBPF v0/v1) is INACTIVE on mainnet-beta and devnet as of 26 Oct
