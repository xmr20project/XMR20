3. TRUST ASSUMPTIONS (summary; details in 01)
  - Groth16 soundness depends on the setup party having destroyed its randomness: FALSE for every existing set (single party,
    owner machine). Soundness is therefore NOT claimed. Zero knowledge holds only if the proving key is the honest one for the
    verifying key: distribution is authenticated (01 §3), the setup itself is not production-safe (08).
  - The ledger domain binds genesis, both verifying keys and the issuer key; all admission (indexer, issuer, holder) is the
    same pool.rs. A record is admitted iff proof, auth and binding signatures verify, the anchor is a known root, every
    nullifier is new.
  - The issuer key is a synthetic file; credits are trusted to the issuer. Redemptions/payouts are gated (05).
  - The daemon is trusted as any Monero wallet trusts its node (decoy bias, eclipse); the holder additionally cross-checks the
    RingCT output count against its own replay.
  - The holder trusts the manifest its build ships; a modified build is out of scope of the manifest control.
  - The journal is a per-installation convenience; the nullifier set is what prevents double spends; two installations with
    one phrase CAN conflict (the loser's carrier fee is lost) — documented, not fixable by the protocol.

4. KEY DERIVATION AND SECRET BOUNDARY (01 §4-5, KEY-SCHEME.txt)
  root = the account's 32-byte Monero private spend key; token spend key = keyed BLAKE2b-256(root, "XMR20-TKD1", "xmr20/private-
  token/spend-key"||LE32(account)); Penumbra key schedule from it; native keys = the standard Monero schedule from root. The
  viewing key leaves the engine only on explicit export. Secrets live in wasm linear memory while unlocked; no constant-time
  claim; memory not scrubbed on lock. In the research harnesses the "phrase" is a synthetic 32-byte root file (never a real seed).

5. PUBLIC METADATA (02; measured on stagenet 24 Oct 2026)
  Carrier transactions are recognisable: 1,056-byte tx_extra (XM3) / 985-byte (XB3), carriers 2,533-2,539 B / 2,462-2,466 B,
  stagenet fee 20,000 piconero/byte (50,660,000-50,780,000 piconero per transfer; NOT a mainnet figure). Public per record:
  anchor, nullifiers, value commitments, rk, ciphertexts, proof, signatures; for XB3 also kind, asset, amount, binding, issuer
  signature. The carrier's ring/key image/change chain is standard Monero metadata; the record contains no native field
  (03 regression: 1,395 checks, 0 hits). Nothing hides that a transaction is a carrier.

7. UNRESOLVED FINDINGS AND OPEN QUESTIONS (ranked; details 06 §E and §F, 07)
  1. Soundness/malleability of the XM3/XB3 composition (shared randomizer, one rk/auth, public amount in the binding
     signature, issuer authorization) — REVIEW.
  2. Disposable single-party setups — ceremony per 08 — PRODUCT + CODE + REVIEW.
  3. Compact payload codec confidentiality/integrity — REVIEW.
  4. XMR20-TKD1 coupling of token keys to the Monero spend key — REVIEW/PRODUCT.
  5. Carrier construction in wasm: decoy faithfulness, fee model, dummy-output fingerprint, change-chain linkage — REVIEW.
  6. Journal/recovery semantics: anything causing inflation, lost notes or a false "completed" beyond the documented fee-loss
     cases (two installations; stale signed carrier re-sent elsewhere) — REVIEW of RECOVERY-CASES.txt + holder-process.mjs.
  7. Rollback loss for bridge payouts and native trading (05) — unchanged; additional confirmations or wallet reservations do
     not eliminate it — PRODUCT/RESEARCH.
  8. No constant-time or side-channel review of wasm proving/signing; memory erasure limits — REVIEW/PRODUCT.
  9. Verifier-side: the indexer/issuer trust one daemon (no independent chain observation in the roles) — CODE.
