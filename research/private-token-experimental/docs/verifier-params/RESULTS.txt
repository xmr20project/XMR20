THE GAP
Stage 1 authenticated parameters on the HOLDER side only. The issuer and indexer roles (lab binary) loaded
parameters.json and the proving keys from a directory with point validation and a verifying-key equality check, but
no manifest: a substituted or corrupted parameter directory would have been accepted if internally consistent, and
nothing bound the roles to the holder's parameter set, protocol version or network.

  src/chain.rs  load_pk(path)               deserialize_uncompressed_unchecked + full point/subgroup checks

                                            setup mode writes a set and is untouched
  No other path reads parameter files; records are verified only through Params (normal_vk/boundary_vk/issuer_vk).

WHAT CHANGED (hardened lab crate)
- A trusted manifest (format XMR20-PARAMS-1) is REQUIRED for every role, given as `--trusted-manifest <path>`,
  a path independent of the parameter directory; optionally its sha256 is pinned (XMR20_TRUSTED_MANIFEST_SHA256).
  Without the flag the role refuses to start ("--trusted-manifest <path> is required (no unauthenticated parameter
  loading)").
- Manifest validation: format; protocol domain label; transfer/boundary circuit shapes compiled into the binary
  (XM3 996/3/2, XB3 925/3/1); network kind offline-fakechain; genesis = config.chain; ledger domain = config.domain
  and recomputed; issuer key and verifying keys consistent; well-formed pins.
- parameters.json: exact length + sha256 against the manifest BEFORE parsing; then field-by-field equality with the
  manifest's configuration ("describes another ledger or version").
- Proving keys (issuer): exact length + sha256 BEFORE deserialization, then the existing point validation and
  verifying-key equality. The indexer loads no proving keys and is bound through parameters.json + manifest.
- Network identity at startup: the daemon's block-0 hash must equal the manifest's genesis.
- The ready line reports the trusted manifest label and sha256; the test backend starts the roles with a manifest
  copied OUTSIDE the parameter directory (run/trusted/manifest.json) and surfaces any refusal as
  "ROLE REFUSED TO START: …" (startBackend throws; nothing runs on unauthenticated parameters).
- Consistency with the holder: the holder's shipped manifest and the roles' trusted manifest are the same file
  (params/test-v1/manifest.json); the holder refuses a server whose parameters.json differs, the roles refuse a
  directory whose files differ, so a holder and the roles can only agree on one parameter set.
