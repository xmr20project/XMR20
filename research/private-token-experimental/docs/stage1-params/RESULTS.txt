A. THE GAP AND WHAT CLOSED IT (details: PARAMETERS.txt)
================================================================================================
Before: the extension downloaded the 83 MB / 64 MB Groth16 proving keys from the test backend and
checked only the embedded verifying key against the ledger domain. Query vectors were not
authenticated; the backend's per-run sha256 was information from the same server, not a trust anchor.
Now:
  - params/test-v1/ is ONE fixed, labelled test parameter set ("DISPOSABLE TEST SETUP — NOT
    PRODUCTION"); the backend serves its files unchanged instead of generating a setup per run.
  - params/test-v1/manifest.json (format XMR20-PARAMS-1) pins exact byte length + sha256 of
    normal.public-pk, boundary.public-pk and parameters.json, each proving key's verifying key, the
    ledger domain, issuer key, chain genesis, network kind, protocol/domain label, key scheme and the
    record shapes (XM3 996 B 3-in/2-out, XB3 925 B 3-in/1-out).
      manifest sha256    ae7ba302194ca3e6f85bd045a653f58026a4fcda9141b1ed8a86600f31611e66
      normal.public-pk   82,675,440 B  8152016c33b1f4bb10da5c2de242b38763bb7461fac3d611dcbee0306326aced
      boundary.public-pk 64,409,328 B  b9b5c8269adf6377480b4713c8449bc28170eb4b3ad5ed00c08b981886bc6120
      ledger domain      759e56ff75367217038d9b5f85f6b878bf3212016922bb2a3891ea4fa6726eb8
  - The manifest ships INSIDE the extension build (vendor/parameters-manifest.json) and its sha256
    is compiled into the holder worker bundle (__PARAMS_MANIFEST_SHA256__). The worker refuses a
    manifest whose hash differs from the compiled constant.
  - wasm engine (`params` op) requires the manifest, validates it (format, protocol label, scheme,
    compiled record shapes, network, genesis, recomputed domain, consistent verifying keys) and
    refuses a server configuration that differs in any field ("different ledger or version").
  - Every parameter file, downloaded or cached, is authenticated over its COMPLETE contents (exact
    length, then sha256) BEFORE any parsing: once in the loader (holder-params.js) and again inside
    the engine's set_blob before deserialization. Rejected bytes are never cached; a cached entry
    that fails is deleted and re-downloaded; an interrupted download is discarded whole.
  - Order in a send/redeem: select -> reserve -> AUTHENTICATE+LOAD proving key -> prove -> publish.
    A refused file stops with "Parameters refused: … Nothing was proved or published." and the
    journal reservation is released.
Still true: the shipped setup is disposable and single-party; authenticating its distribution does
not make it production-safe. The separate production work (circuit freeze, MPC ceremony, signed
provenance, verifier-side manifest checks) is listed in PARAMETERS.txt.

================================================================================================

host's job and the worker does it: documented); stale keep-alive sockets in the same-process Node
tests (all loader fetches now `connection: close`); borrow/Debug compile errors.
Unresolved / not claimed:
  - The parameters are a disposable single-party setup; soundness/zero-knowledge against the party
    who ran it is not claimed. Production needs an MPC ceremony and reviewed circuits.

    manifest. The wasm itself does not pin the manifest (the host does).
  - Verifier-side roles (indexer/issuer/operator) still load parameters from disk with point
    validation but without a manifest check.
  - Bridge finality / rollback-loss counterexample unchanged (research/privacy-extension-20261022/
    ERRATUM-exposure-window.txt): window cap is a payout-rate control, 400 exposed under a 200 cap.
  - No security review; proving ≈30 s single-threaded; 147 MB of parameters per install; relay-paid
    carriers (addressed in stage 2, research/privacy-carrier-20261023).
