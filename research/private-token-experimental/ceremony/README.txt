PROOF PARAMETERS — WHAT EXISTS, WHY IT IS NOT ACCEPTABLE FOR FUNDS, AND THE SETUP PROCEDURE FOR OUR CIRCUITS
research/privacy-release-candidate-20261025/ceremony — 25 October 2026. Independent review: NOT performed. Production ceremony: NOT run.

1. WHAT A "PROOF PARAMETER" IS, PLAINLY
  Every private transfer carries a Groth16 zero-knowledge proof. Groth16 needs a one-time SETUP per circuit that produces a proving key
  (wallets use it to make proofs) and a verifying key (indexers use it to check them). The setup is derived from random secrets. Anyone
  who still knows those secrets can forge proofs — create tokens from nothing — and no verifier can tell. The secrets are "toxic waste".

2. WHAT EXISTS TODAY AND ITS RISK
  Two circuits, both ours (they COMPOSE Penumbra's audited sub-circuits into one proof each):
    normal   XM3 private transfer  = 3 SpendCircuit + 2 OutputCircuit   135,684 constraints, 17 public inputs, degree 2^18
    boundary XB3 boundary record   = 3 SpendCircuit + 1 OutputCircuit   121,809 constraints, 15 public inputs, degree 2^17
  (R1CS digests in runs/ceremony-rehearsal/ceremony.json; the Penumbra sub-circuits are byte-identical to penumbra-sdk-shielded-pool
  2.1.1 — the vendored copy only makes two constructors public.)
  Every parameter set in this project (params/test-v1, test-other, stagenet-v0, stagenet-v0-trusted) was generated by ONE process on
  ONE laptop with ark-groth16's generate_random_parameters (the lab's `setup`). The secrets were never written to disk, but nothing can
  PROVE that, and the machine, its memory and its operator are a single point of trust. Risk, stated plainly: whoever controlled that
  process at that moment could forge any amount of any private token verified against those keys. Acceptable for a test chain whose
  tokens are worthless; never for a ledger that backs real Solana tokens.

3. THE CORRECT PROCEDURE FOR OUR CIRCUITS (what a production ceremony must do)
  Groth16 setups are run as a multi-party ceremony: many participants each add their own secret randomness on top of the previous
  result and destroy it. The output is sound if AT LEAST ONE participant in each phase destroyed their secret; every contribution
  carries a proof of knowledge linking it to its predecessor, so the whole chain is publicly checkable.
  Phase 1 ("powers of tau", α, β): circuit-independent for a given degree; needs degree >= 2^18 for `normal`. Options: run our own
    (the rehearsal does), or REUSE a public phase 1 of sufficient degree on BLS12-377 (the same curve). Penumbra's 2023 phase 1 had
    over 15,000 contributors, BUT its degree is NOT verified here: the proof-setup code runs phase 1 per circuit at that circuit's own
    degree (penumbra-sdk-proof-setup 2.1.1 all.rs), so a transcript of degree >= 2^18 exists only if one of Penumbra's circuits needed
    it, and the spec names no publication location (PROOF-SYSTEM-ALTERNATIVES.txt 6). Until established, plan for participants to
    contribute to phase 1 too.
  Transition: deterministic from the final phase-1 result and the exact R1CS of the circuit (the R1CS digest binds it).
  Phase 2 (δ, circuit-specific): MUST be run for our two circuits — no public ceremony covers composed circuits. Every participant
    runs `contribute … phase2` once per circuit on their own machine with their own randomness.
  Finalisation: combine phase 1 + transition + phase 2 into the proving key; the verifying key is inside it. Publish the keys' digests,
    the full transcript (every contribution, hash-chained) and the attestation; third parties re-run `verify` from the source.
  Binding: the trusted manifest (XMR20-PARAMS-1) pins parameters.json, both key files (bytes + sha256) and now the attestation; roles
    and holders refuse any file that does not match (existing verifier-side authentication, exercised by holder-params/verifier-params
    tests and by ceremony-rehearsal.test.mjs with a foreign manifest).
  Alternative considered and REJECTED (25 Oct, owner's observation): carry FIVE separate Penumbra proofs per record and reuse Penumbra's
    published ceremony keys. The proof field would grow 192 -> 960 bytes; the XM3 carrier already uses 1,056 of the 1,060 bytes that
    Monero nodes relay in tx_extra (relay policy, not consensus), so the record would no longer fit in one Monero transaction. Shrinking
    to one input and one output per record would split ordinary transfers across several transactions (more fees, partial settlement,
    the ordering problems the settlement work avoids). The combined proof is what keeps one transfer in one transaction, and it needs
    keys made for it: an own ceremony with independent participants is the realistic path.

4. WHAT THE TOOL HERE DOES (ceremony/src/main.rs over a vendored penumbra-sdk-proof-setup 2.1.1)
  init -> contribute (phase1) x N -> transition -> contribute (phase2) x N -> finalize -> verify, with the transcript in ceremony.json
  and every contribution as a file; `verify` recompiles the circuits from source, checks the R1CS digests, replays BOTH logs
  (every contribution must validate AND link to its predecessor), recomputes the transition, recombines the keys and compares them
  byte-for-byte with the parameter files and the manifest. Refusals exercised in ceremony-rehearsal.test.mjs: flipped byte in a
  contribution, substituted key file, foreign chain, transition from the bare root, production-looking label, foreign manifest.
  Rehearsal performed here: three contributions per phase per circuit by PROCESSES ON THIS LAPTOP (participants "rehearsal-1/2/3").
  That is zero independent participants. The output (params/ceremony-rehearsal-v1) is therefore DISPOSABLE — exactly as trustworthy as
  the single-party sets it mirrors — and is labelled so in ceremony.json, attestation.json and manifest.json. It proves the WORKFLOW
  (contribute / verify / bind / prove / verify-proof), not the parameters.

5. INSTRUCTIONS FOR GENUINE INDEPENDENT PARTICIPANTS (prepared; nobody has been contacted — owner decision pending)
  Who counts: a person who is not the operator, on hardware the operator does not control, ideally offline during contribution.
  Several AI agents, processes, VMs or accounts on the operator's machine count as ONE participant (the operator).
  Each participant, once per circuit and phase they join:
    a. Obtain the ceremony repository state from the coordinator: ceremony.json + all contribution files so far (or the coordinator's
       published hash of the last contribution). Verify first:   xmr20-params-ceremony verify-log <dir> <circuit>   (TODO before any
       real ceremony: expose the log-only verification as its own command; today `transition`/`finalize` perform it).
    b. Build the tool from the pinned source yourself (ceremony/, Cargo.lock) — do not accept a binary from the coordinator.
    c. Run:  xmr20-params-ceremony contribute <dir> <circuit> phase2 --participant <your-handle> --entropy "<dice rolls / long random text>"
       on a machine you control; the tool mixes your text with the OS RNG. It writes <circuit>/phase2/NNN-<handle>.bin.
    d. Publish the printed hash of your contribution somewhere the coordinator cannot edit (your own channel), then send the file.
    e. Destroy the machine state you can (reboot; delete the directory). Keep the printed hash.
  After finalisation every participant checks: their hash appears in attestation.json, `verify` passes on a fresh checkout, and the
  manifest that wallets ship pins exactly those key digests.
  Coordinator duties: publish the degree, R1CS digests and tool commit BEFORE the first contribution; never run two coordinators;
  reject late or unlinked contributions (the tool does); publish the full transcript and attestation.
  Minimum for the product: at least several participants who are independent of the operator AND of each other for phase 2 of BOTH
  circuits (phase 1 may be inherited from Penumbra's public ceremony after the degree is confirmed). The exact number is a product
  decision; the soundness argument needs one honest participant per phase, the credibility argument needs more.
